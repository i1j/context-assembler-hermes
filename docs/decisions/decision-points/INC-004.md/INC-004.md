# INC-004: state.db 重复写入 — `conv_hist[:]=_backup` 破坏 `id()` 去重

**父节点:** [[R-000]], [[C-027]]

**Impact:** 受影响会话 state.db 消息行呈线性增长（每轮翻倍），严重影响长对话数据一致性。
首现会话: `mqujr62cl07h4r` 附近（CA 插件 v5.10 后期改动后首次部署）。

**Root Cause:** `post_llm_call_v5` 中 `conv_hist[:] = [{**m} for m in _backup]` 创建全新 dict 对象，
破坏 Hermes `_flush_messages_to_session_db()` 的 `id()` 去重 → 每轮所有消息重写一次。

## Bug 链详解

```
┌─ compress 入口 ──────────────────────┐
│  _full_backup = [{**m} for m in      │  ← Hermes messages 快照
│                 conversation_history] │
└──────────┬───────────────────────────┘
           │
           ▼
┌─ A-stage 过滤+替换 ──────────────────┐
│  messages[:] = filtered  ← 删 FAR 行 │
│  + A-stage 修改 content              │
└──────────┬───────────────────────────┘
           │
           ▼
┌─ LLM 调用 ──────────────────────────┐
│  返回 assistant 回复 + tool 行       │
└──────────┬───────────────────────────┘
           │
           ▼
┌─ post_llm_call ──────────────────────┐
│  改前: conv_hist[:]=[{**m} for m in  │
│                    _backup]          │
│          └── 每个 dict 被 {**} 解包   │
│              重建 → 全新 Python 对象  │
│                ↓                     │
│  改后: 仅清掉 _full_backup，不写      │
│        state.db（数据早已由            │
│        _flush_messages_to_session_db  │
│        在 compress 前写入）            │
└─────────────────────────────────────┘
```

## 第一次修复（已废弃）：互补双路径落盘

**2026-06-26 实施的方案，在 2026-06-27 发现引入用户消息双写缺陷后被废止。**

原方案：`_full_backup` 直写 state.db + `_flush_messages_to_session_db` 写新消息。问题在于
`_full_backup` 包含用户消息，而用户消息已在 compress 前被正常流程写入了 state.db →
每条用户消息多写一次。详见 [[INC-005]]。

## 最终修复：去掉 `_full_backup` 写 state.db

`_full_backup` 的唯一目的是作为 sentinel：post_llm_call 检测到它存在 →
知道 compress 已发生 → 跳过 `conv_hist[:]=_backup` 模式。**不写 state.db。**

原因：所有被 A-stage 删除/修改的原始数据（FAR thought/tool 行、替换为 Hdl 的 content）
在 compress 触发之前的对话流程中，已经全部由 `_flush_messages_to_session_db` 写入过 state.db。
A-stage 只在内存中修改 `conversation_history`，不影响 state.db 中的已写数据。

```python
# 改后
_backup = getattr(self, "_full_backup", None)
if _backup is not None:
    self._full_backup = None
    # 不需要写 state.db——原始数据早已写入
```

| 路径 | 内容 | 去重机制 |
|------|------|----------|
| `_flush_messages_to_session_db`（正常路径） | All | `id()` 去重，每轮只补增量 |
| `_full_backup` | 不再写 state.db | 仅作 sentinel |

## 影响范围

- 每次 CA 触发的 compress 轮都会触发（只要有 A-stage 处理）
- 无 CA 处理的轮次不受影响（`_flush_messages_to_session_db` 正常去重）
- state.db 累积冗余行，不直接影响 LLM 回复质量（会话恢复读的是 `_full_backup`）

## 为什么之前没发现

- `_flush_messages_to_session_db` 的 `id()` 去重是 Hermes 原生机制，CA 代码从未主动破坏它
- 前版本（v5.0）`_simple_mutation_mode_v5` 通过 `messages[:]=filtered` 修改引用 → 共享同对象池 → `id()` 正常工作
- 某次 bug 修复中把改引用改为 `conv_hist[:]=[{**m}...]` → 意外切断 `id()` 链，未加注释/审查

## Evidence

- 代码: `post_llm_call_v5()` in `plugins/ca_assembler/__init__.py`
- DB 数据: `hermes protools state-db messages` 表轮次重复行
- 回退验证: 去掉 `conv_hist[:]=_backup` 后 state.db 无重复
