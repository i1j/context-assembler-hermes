# CA v5 方向：缓存友好 + 反馈调优 — 试验计划

> 日期：2026-06-06（原始）/ 2026-07-01（更新）
> 背景：基于缓存前缀匹配机制的分析，识别出 CA 当前 assemble() 中存在两个缓存破坏因素（去重方向、Head 区），
> 以及一个长期改进方向：通过反馈闭环实现拣选参数自动调优。
> 本文档记录两个方向的试验方案。
>
> **状态更新（v4.5.1）**：方向一「去重方向」和「Head 区移除」已在 v4.5.1 中实现。
> 剩余方向二「参数自动调优」仍为开放研究课题。

---

## 方向一：结构改进（确定性收益）

### 1.1 去重方向改为向前引用

**当前行为（留最后）：**

```
新的重复出现 → 创建标记指向最后出现的幸存者
              → 前一次标记位置被更新 → 前缀变化
```

**改为（留最先，向后引用）：**

```
首次出现：保留完整内容，位置固定不动
后续重复：只在末尾追加轻量标记 (同[~/N])
          → 首次位置不变 → 前缀稳定
```

**改动范围：**
- `ca/__init__.py` — `_deduplicate_messages()`：从"保留最后一条完整"改为"保留第一条完整"
- 标记生成：从 `(同[~/N])`（N = 最后出现位置）改为 `(同[~/N])`（N = 首次出现位置，不变）

**验证：**
- 同一段历史对话跑两次 assemble()，前 N 轮 token 序列完全一致（只有末尾标记行数不同）
- 缓存命中率：对比改前改后的 cache_miss_tokens 变化

### 1.2 Head 区移除

**当前行为：**

```
assemble() 固定保留最近 3 轮为完整对话（Head 区），其余轮次压缩为 L0/L1。
每轮第 t+4 轮从 Head 区消失，转为 Middle L0 → 前缀断裂。
```

**改为纯拣选驱动：**

```
所有历史轮次统一由评分函数（BM25 + embedding）决定 L0/L1/L2。
不设固定 Head 区。每轮只有追加的当前轮是新内容。
```

**改动范围：**
- `ca/__init__.py` — `_compute_turn_plan()` 或 `_build_messages_from_plan()`：移除 Head 区的强制 3 轮保留逻辑
- 保留 Tail 区（当前轮）
- 确保不出现"没有任何行升级到 L1/L2"时上下文为空——至少保留最近 1 轮的 L2 作为保底

**验证：**
- 同一话题的连续两轮请求，前 N 轮的 token 序列完全一致
- 对比改前改后的 cache_miss_tokens 比例
- 确保拣选机制在极端情况（所有轮次分数都低）下仍有保底输出

## 方向二：参数自动调优（反馈闭环）

### 2.1 问题定义

CA 当前的 BM25 + embedding 评分函数 F 有一组可调参数 θ：

```
θ = { BM25_k1, BM25_b, embedding_weight, upgrade_threshold, ... }
```

目标：找到 θ* 使得评分函数 F_θ 的拣选结果与云端 LLM 的实际信息需求一致。

### 2.2 反馈信号

困惑在于如何定义"拣选正确"的观测信号。不依赖 LLM 的外部搜索行为（因为 LLM 搜索可能有其他原因），而是使用更直接的方法：

**方案 A：受控实验 + 总成本反馈（推荐）**

```
1. 在当前 θ 基础上做小幅扰动 δ
2. 对同一批历史对话，分别用 F_θ 和 F_{θ+δ} 构造上下文
3. 用这两种上下文分别调云端 LLM 完成同一组测试问题
4. 对比总成本（prompt_tokens + completion_tokens + 工具调用轮次数）
5. 保留成本更低的那组参数
6. 重复

不需要理解"为什么 δ 好/坏"——只需要观察总成本的变化方向。
这是无模型的黑盒优化。
```

**方案 B：评分校准（辅助）**

```
对每行 tᵢ：
  score(tᵢ, Q) = BM25(tᵢ, Q) × w_bm25 + embedding(tᵢ, Q) × w_emb

当 LLM 在某轮的多轮工具调用中反复读取了某行的历史内容时（通过对比文件路径）：
  该行在后续对话中应该被更优先地升级
  不直接调评分函数，而是维护一个「行级别的热力值表」作为评分偏移
```

### 2.3 优化算法

**推荐：CMA-ES 或简单的随机爬山**

```
1. 当前参数 θ = (k1, b, w_emb, threshold, ...)
2. 对每个参数，定义合理的扰动范围（±10%~±30%）
3. 生成 N 组扰动候选 {θ₁, ..., θₙ}
4. 对每组候选，用历史对话做仿真：
   a. 用 F_θᵢ 对历史中的每个 Q 做拣选
   b. 累计 prompt_tokens（命中/未命中分计）+
      completion_tokens（按平均输出长度估算）
   c. 不考虑工具调用轮次变化（仿真无法准确模拟）
5. 选出总成本最低的 θᵢ
6. 在该 θᵢ 附近继续扰动 → 重复
```

**离线仿真不完美——无法衡量"拣选偏差导致 LLM 多跑工具调用"的损失。**
但可以作为初次筛选，选出有希望的 θ 候选，再部署到线上做 A/B 测试。

### 2.4 线上 A/B 测试方案

```
Session 分组：
  对照组：当前 θ₀
  实验组：新 θ'

每轮记录：
  prompt_tokens（命中/未命中）
  completion_tokens
  工具调用次数
  对话轮次数

评估指标：
  总 token 成本（按 cache_hit/miss 计价）
  对话完成度（是否在合理轮次内完成任务）
  用户满意度（如有反馈）

收敛条件：
  θ' 在连续 N 次 A/B 测试中均优于 θ₀ → 采纳为新默认
  θ' 连续 2 次劣于 θ₀ → 回滚，缩小扰动幅度
```

## 优先级建议

| 序号 | 项目 | 预期收益 | 实现成本 | 风险 |
|------|------|----------|----------|------|
| 1 | 去重方向改向前引用 | 中（去重场景下缓存提升） | 低（改动 1 个函数） | 低 |
| 2 | Head 区移除 | 高（每轮都受益） | 中（需重审分层逻辑） | 中（需确保保底） |
| 3 | 参数自动调优 | 长期、持续 | 高（实验框架 + 仿真管线） | 中（反馈信号不完美） |

**建议顺序**：1 → 2 → 3。1 和 2 是确定性改进，先落地后评估效果，再决定是否需要 3。
